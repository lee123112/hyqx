> **【v4.2 重大变更 · 2026-10-19】** ① `/predict` 升级**双协议**：形态一 `POST /predict?detection=<算子标识>`（`multipart/form-data`，`file` 必传）+ 形态二 `POST /predict?operatorId=Mxx`（`application/json`）；② 形态二响应统一为 `data{operator, status, outputFile, result}`，**不再返回 `lineageFile`**，`outputFile`（`crossmodal-files-v1`）在中间调用与阶段末**都返回**；形态一返回 JSON 首字段 int `status`（判定型 1 通过/0 不通过，处理型 1 成功/0 失败）；③ **血缘文件/阶段归档/运输输出全部停用**（`lineage.json`、`stage_context.json`、`stage_lineage.jsonl`、`stage_artifact.zip` 不再产出）；④ 记录级 `status` 统一改为 int 双字段（`status` + `process_status`）。本文第 4.4.3、5、6.3、7.2、7.3 节及所有出现 `lineageFile` 的示例为 **v4.1 历史契约**，当前接口以 `README.md` 第 0 节与 V4.2 规范文档为准。

本包把跨模态产线的 **26 个算子（M01–M26）** 打成一个镜像、一个入口、一个端口，
调用方只需用 `operatorId` 选择算子，不需要分别对接 26 个服务。

> **【算子标签 · 2026-10-22】** 按规格表（v4.2 建议修订版_新）G 列「工具类型=系统功能」，
> 以下 **7 个算子标记为「平台提供｜免研发免测试」**（各算子根目录已落 `operator_tags.json`）：
> **M01 接入多模态批次、M02 核验场景编号、M22 生成跨模态Token、M23 压缩交付对齐语料包、
> M24 抽检并回写质量报告、M25 管理人工复核任务、M26 生成交付样例**。
> 它们在链路中作为平台依赖照常运行（登记/场景核验/Token/打包/回写/人工复核/样例），
> 但不纳入本团队的研发与单元测试范围；其余 19 个算子（规则型 12 + 小模型 7）为自研自测范围。

- **全本地推理**：所有模型权重随各算子目录内置（`<算子目录>/weight/`），运行期**不联网、无公网模型 API、不调用大模型**；
- **只读写 `OUTPUT_DIR/<uniqueId>/`**：任务按 `uniqueId` 隔离，拒绝目录穿越；
- **单入口端口 `8100`**：26 个算子的内部端口（8101–8126）只在容器内可见。

## 0. 快速开始（5 步）

```powershell
# 第 1 步：进入包根目录并安装依赖（权重已内置各算子，无需设置 MODEL_ROOT）
cd "G:\HYQX\算子\跨模态\crossmodal_v1.0"
python -m pip install -r requirements.txt
$env:OUTPUT_DIR = "G:\data\op_output"

# 第 2 步：启动前自检（应看到 operatorCount=26、okCount=26，且 weightBundles.missing 为空）
python inference.py --preflight

# 第 3 步：启动统一入口
python -m uvicorn inference:app --host 0.0.0.0 --port 8100

# 第 4 步：健康检查；ready 还会显示已就绪的子算子数量
curl.exe http://127.0.0.1:8100/health
curl.exe http://127.0.0.1:8100/ready

# 第 5 步：上传 + 调用（M01=接入多模态批次，阶段首算子省略 inputFile）
curl.exe -X POST "http://127.0.0.1:8100/uploadFile?uniqueId=task01_file01&operatorId=M01" -F "file=@demo.jsonl"
curl.exe -X POST "http://127.0.0.1:8100/predict?operatorId=M01" -H "Content-Type: application/json" `
  -d "{\"uniqueId\":\"task01_file01\",\"isLastOperator\":true}"
```

> ⚠️ **Windows PowerShell 下请写 `curl.exe`**：`curl` 是 `Invoke-WebRequest` 的别名，
> 不认 `-X`/`-F`/`-H` 这些参数。Linux/macOS 直接用 `curl` 即可。

### 0.1 使用前的三个判断

1. **先看 `code`，再看 HTTP 状态码**：业务成功必须同时满足响应体 `code=0`；`HTTP 200` 也可能是业务失败。
2. **阶段首不传 `inputFile`，阶段内必须原值回传**：阶段内后续算子使用上一响应
   `data.outputFile` 的原值（`crossmodal-files-v1` 内容对象 / 其入口引用），不要手工拼路径或改成宿主机路径。
3. **`data.outputFile` 在每次调用都返回**（v4.2 起中间调用也返回内容对象，由平台物化后作为下一算子 `inputFile`）；
   `data.result` 为业务摘要（含记录级 `status`（int）+ `process_status`）。

### 0.2 交付包完整性检查

在交付服务器上建议先执行下面三条命令。它们不启动子算子，也不会加载模型：

```powershell
cd <发布包根目录>
python -X utf8 -B inference.py --preflight
python -X utf8 -B -c "import json;json.load(open('map.json',encoding='utf-8'));print('map.json OK')"
```

`--preflight` 的判定标准是 `operatorCount=26` 且 `okCount=26`。本次对交付文件夹的复核结果为 **26/26**。
注意：不要用 `python -m compileall` 直接在本包内跑语法检查（会在包内写 `__pycache__/`，压缩前需再清理）；
本包核验用的是不落盘的逐个 `compile()` 检查。

## 1. 概述

### 1.1 是什么

一个**算子池服务**：进程内按 `map.json` 注册表管理 26 个算子，首次调用某算子时
按需拉起该算子的服务进程（`cwd=<算子目录>`，`uvicorn app:app --port <该算子端口>`），
并把它自己的三个接口原样转发出去。

对调用方来说：**一个端口 + 三个接口 + 一个 `operatorId` 参数**。

### 1.2 七个业务阶段（26 个算子）

| 阶段 | 算子数 | 包含编号 |
|---|---:|---|
| 输入核验 | 3 | M01 – M03 |
| 数据清洗 | 5 | M04 – M08 |
| 数据加工 | 11 | M09 – M19 |
| 数据质量评估 | 2 | M20 – M21 |
| 样本构建 | 1 | M22 |
| 数据集交付 | 1 | M23 |
| 人工抽检复核 | 2 | M24 – M25 |
| 交付样例 | 1 | M26 |

> 同一大阶段内的多个算子**共用一个 `uniqueId`**，按阶段内顺序逐算子调用；
> 跨大阶段时把上一阶段产物**重新上传**为新的 `uniqueId`（详见第 5 节）。

推荐的功能顺序为：

```text
M01–M03 输入核验
  → M04–M08 数据清洗
  → M09–M19 数据加工
  → M20–M21 数据质量评估
  → M22 样本构建
  → M23 数据集交付
  → M24–M25 人工抽检复核
  → M26 交付样例
```

这是一条**编排参考顺序**，服务不会自动替调用方串联 26 个算子。每个大阶段结束后，调用方需要保存阶段末
`data.outputFile`，按第 5 节的方法还原文件，再用新的 `uniqueId` 进入下一阶段。表中标记为“默认关闭”的算子
必须在该次 `/predict` 的 `config.enabled`（或该算子约定的 `overrides.enabled`）中显式打开。

### 1.3 与「预训练文本算子池」的差异（重要）

本包的接口契约与 `预训练文本算子使用文档.md` 所描述的文本算子池**不完全相同**，对接时请以本文档为准：

| 项目 | 文本算子池 | 本跨模态算子包 |
|---|---|---|
| 业务参数字段 | `params` | **`config`**（部分算子写作等价的 `overrides`，见 4.4.2） |
| 血缘回传 | 请求需原样回传 `lineageFile` | **不需要**（v4.2 起不再产出/返回血缘文件） |
| 门禁字段 | 有 `terminal` / `stopChain` / `qualityTag` | **没有**，编排分支由调用方按各算子产出的记录自行判断 |
| 阶段末返回 | `outputFile` 为 `tmp://` 文件名 | `outputFile` 为 **`crossmodal-files-v1` 内容对象**（文件内容内联） |
| 模型 | 调用服务端 Qwen3-VL | **全部本地权重**（CLIP / Whisper / wav2vec2 / BERT / YOLO） |

## 3. 部署与启动

### 3.1 Docker（推荐）

#### 3.1.1 构建镜像（下载慢可换源）

默认从 Docker Hub / PyPI / Debian 官方源下载。国内或内网构建慢时，可覆盖三个构建参数
（`PYTHON_IMAGE` / `PIP_INDEX_URL` / `APT_MIRROR`），只影响下载来源，不写入镜像：

```bash
# 官方源（默认）
docker build -t opcrossmodalpool:1.0.0 .

# 国内镜像源示例（按你们实际可用的加速地址替换）
docker build -t opcrossmodalpool:1.0.0 \
  --build-arg PYTHON_IMAGE=docker.m.daocloud.io/library/python:3.11-slim \
  --build-arg PIP_INDEX_URL=https://pypi.tuna.tsinghua.edu.cn/simple \
  --build-arg APT_MIRROR=mirrors.tuna.tsinghua.edu.cn .
```

| 构建参数 | 默认值 | 说明 |
|---|---|---|
| `PYTHON_IMAGE` | `python:3.11-slim` | 基础镜像；Docker Hub 慢时换成加速地址或内网 registry（须为 Debian slim 变体） |
| `PIP_INDEX_URL` | `https://pypi.org/simple` | pip 源；可换清华 / 阿里云 / 内网 PyPI |
| `PIP_TRUSTED_HOST` | 空 | 私有 HTTP PyPI 的 host（https 源不用填） |
| `APT_MIRROR` | 空 | Debian apt 镜像主机名（只填主机，如 `mirrors.tuna.tsinghua.edu.cn`）；不填用官方 `deb.debian.org` |
| `PIP_TIMEOUT` / `PIP_RETRIES` | `120` / `5` | 慢网络下的下载超时与重试次数 |

用 compose 构建时，在包根目录 `.env` 写入同名变量（或命令前加环境变量）后执行 `docker compose build`，
compose 会自动透传（`docker-compose.yml` 已配置 `build.args`）。

> 镜像里 `torch`/`torchvision` 默认装 PyPI 的 CUDA 版轮子（下载量约 2 GB 量级，是构建慢的主要部分）；
> 如果目标服务器是纯 CPU，可按 `requirements.txt` 注释换成官方 CPU 轮子（`+cpu` 通道），下载量会明显下降。
> 换源只加速下载，不改变依赖版本。

#### 3.1.2 启动（compose，首选）

包根目录已带 `docker-compose.yml`，首选 compose 部署（一个镜像、一个入口、一个端口）：

```bash
docker compose up -d --build        # 默认宿主机 17059 → 容器 8100
docker compose ps
curl http://127.0.0.1:17059/health
curl http://127.0.0.1:17059/operators
docker compose logs -f --tail=200
docker compose down
```

可覆盖变量（写同目录 `.env` 或服务器环境变量）：`HOST_PORT`（默认 17059）、`OUTPUT_HOST_DIR`（宿主机产物目录）、
`POOL_AUTOSTART` / `POOL_STARTUP_TIMEOUT` / `POOL_ONLY`、`TZ`；上传/响应限额（`MAX_*`）固定写在 compose 的
`environment` 中，需要调整改该文件；有 Docker CLI 时可用 `docker compose config` 校验变量展开。
`MTY_*` / `TASK_OUTPUT_*` 属 v4.2 停用项，compose 中默认不启用，回滚时按 `.env.example` 配置。

不使用 compose 时，等价的 `docker run` 如下：

```bash
# 运行：v1.0 正式版权重已随算子目录内置进镜像，只需挂输出目录；不再挂载共享 weight/、不再设 MODEL_ROOT
docker run --rm -p 8100:8100 \
  -e OUTPUT_DIR=/data/output -v /host/crossmodal_output:/data/output \
  -e TZ=Asia/Shanghai \
  opcrossmodalpool:1.0.0
```

- 镜像内已执行 `python inference.py --preflight` 自检，构建失败即镜像构建失败；
- 镜像内已安装 `ffmpeg` / `ffprobe` / `tzdata`（#6/#7 与 TZ 日志时间戳依赖）；
- 容器内进程按需拉起（`POOL_AUTOSTART=0` 默认），首次调用某算子会有 **数秒启动延迟**；
- 需要模型预热时设 `-e POOL_AUTOSTART=1`（启动即拉起全部 26 个算子，内存占用更高）。

### 3.2 本地直接运行（联调）

```powershell
# 包根目录
pip install -r requirements.txt
$env:OUTPUT_DIR = "G:\data\op_output"     # 可选，默认 <包根>/output
# 无需设置 MODEL_ROOT：各算子默认加载自身 <算子目录>/weight/
python -m uvicorn inference:app --host 0.0.0.0 --port 8100

# 单算子独立运行（可把 CMA_xxx/ 整体复制到任意位置，目录内已含 weight/）
cd CMA_score_image_text_consistency
python -m uvicorn app:app --host 0.0.0.0 --port 8112
```

### 3.3 启动自检

```powershell
# 检查注册表 + 26 个算子目录关键项 + 逐算子内置权重，不拉起子进程
python inference.py --preflight
```

输出中 `okCount` 应等于 `operatorCount`（26），且 `weightBundles.missing` 为空。若某算子报
`problems`（如「缺少 configs」「缺少内置权重 clip」），说明该算子目录或权重不完整，请重新同步包。

> `--preflight` 只做结构和注册表检查，不验证 GPU、模型推理精度或 Docker 运行环境；
> 模型算子的首次真实调用仍可能因权重加载产生较长延迟。

### 3.4 环境变量

| 变量 | 默认值 | 作用 | 生效范围 |
|---|---|---|---|
| `OUTPUT_DIR` | `<包根>/output` | 结果落盘根目录（`OUTPUT_DIR/<uniqueId>/…`） | 池化 + 全部算子 |
| `MODEL_ROOT` | 空（各算子用自身 `weight/`） | 可选覆盖：外挂统一模型盘时才设置；设置后相对权重路径按此解析 | 模型类算子 |
| `PORT` | `8100` | 池化对外唯一端口 | 池化 |
| `POOL_AUTOSTART` | `0` | `1`=启动即拉起全部算子；`0`=首次调用按需拉起 | 池化 |
| `POOL_ONLY` | 空 | 逗号分隔编号（如 `12,13`），只暴露/启动这些算子 | 池化 |
| `POOL_STARTUP_TIMEOUT` | `60` | 单个算子进程就绪等待秒数 | 池化 |
| `MAX_UPLOAD_BYTES` | 各算子 64–256 MiB | 单次上传限额 | 部分算子（详见各算子 `README.md`） |
| `MAX_RESPONSE_BYTES` | 各算子 64–256 MiB | 阶段末响应体上限，超限**直接失败、不截断** | 部分算子 |
| `TZ` | `Asia/Shanghai` | 血缘时间戳时区 | 全部算子 |
| `MTY_TRANSPORT_ENABLED` | `1` | `0`=关闭 OSS 归档与关系入库（只保留血缘/阶段产物） | 全部算子 |
| `MTY_ARCHIVE_BACKEND` | `auto` | 归档后端：`auto`/`oss2`/`boto3`/`local`/`none` | 全部算子 |
| `MTY_REGISTRY_BACKEND` | `auto` | 入库后端：`auto`/`sqlalchemy`/`sqlite`/`none` | 全部算子 |

| `TASK_OUTPUT_SCAN_ROOT` | 同输出根 | 阶段束扫描根（找同任务同阶段各算子的 run 目录）；算子输出分散在不同卷时才需要设置 | 阶段末算子 |
| `TASK_OUTPUT_LOCK_TIMEOUT` | `600` | 输出目录文件锁等待秒数（并发发布互踩保护，超时放弃本次写入并记 warning） | 阶段末算子 |

## 4. 接口说明

### 4.1 接口总览

池化层对外暴露的接口：

| 接口 | 方法 | 用途 |
|---|---|---|
| `/health` | GET | 池化存活探针（不判断子算子是否就绪） |
| `/ready` | GET | 池化就绪探针（含各子算子状态） |
| `/operators` | GET | 算子清单与子进程状态（排障用） |
| `/uploadFile` | POST | 上传任务输入文件（按 `operatorId` 转发） |
| `/predict` | POST | 执行算子（按 `operatorId` 转发） |
| `/removeFile` | POST | 删除任务工作区（幂等） |

> **单算子容器的 `/health`**：每个算子容器同样提供 `GET /health`（信封式 JSON，返回 `code=0` 与本算子标识），但按交付契约设为 `include_in_schema=False`——它**不出现在** `/openapi.json`（文档只含 `/uploadFile`、`/predict`、`/removeFile` 三个业务接口），容器内探活直接请求 `/health` 即可（2026-10-22 口径统一，26 个算子一致）。

**`operatorId` 的三种写法等价**（大小写不敏感），优先级：`?operatorId=` → 请求头 `X-Operator-Id` → 请求体 `operatorId`：

```text
M12  /  12  /  012                              # 表1 编号
image_text_semantic_scoring                     # 算子英文 id（map.json.operatorId）
CMA_score_image_text_consistency                # 算子目录名
```

> `/uploadFile`、`/predict`、`/removeFile` **必须带 `operatorId`**，否则返回 HTTP 400。
> 请求体里的 `operatorId` 会在转发前被剔除，不影响子算子校验。

> **[v4.2] `detection` 与 `operatorId` 等价**：平台侧 MTY V2 单文件流用 `POST /predict?detection=<算子标识>`（`multipart/form-data` + `file`），
> 与 `?operatorId=Mxx`（JSON，形态二）走同一张注册表；也接受请求头 `X-Detection`。
> 池化层解析路由后会把 `detection` 从转发的查询串与请求体里剔除，子算子不会因该参数报「未知字段」。
> 例：`/uploadFile?detection=data_prescreen&uniqueId=task01_file01`、`/predict?detection=data_prescreen`。
> 旧版池化层（`crossmodal_package_20261011`）不识别 `detection`，此类请求会**立即**返回 400「缺少或无法识别的 operatorId」。

> **[v4.3 新增] 形态一压缩包模式（#3–#21 共 19 个算子）**：业务平台实际只调用 `POST /predict?detection=<别名>`，
> 用 multipart 字段 `file` 直接上传一个 **ZIP 包**（入口 JSONL + 媒体相对路径 + 可选 `manifest.json`），
> **不再需要 `/uploadFile`**。响应为 JSON：首字段 `status`（1=执行成功/0=执行失败）+ 业务指标 +
> `outputFile` **路径引用**（`mode=path-reference`），并同时生成可直接作为下一算子输入的 `<runDir>_form1.zip`。
> `uniqueId` 为**可选**查询参数，缺省时服务端生成 `upload_<YYYYmmdd_HHMMSS_ffffff>`；若显式传入，仍按
> 「任务id_文件id」规则校验（纯数字/单词会被 422 拒收）。完整契约见 §4.4.4，逐算子直传见 §5.2，路径引用见 §7.1。

### 4.3 `POST /uploadFile?uniqueId={任务id}`

把一个任务的输入素材上传到该任务的工作区。

- **query**：`uniqueId`（必填；只允许安全的任务标识，拒绝空值、绝对路径、`..` 目录穿越）；
  **格式必须是「任务id_文件id」（形如 `task001_file01`）**，纯数字或单一词（如 `2113223738925842433`、`smoke01`）会被拒收为 422；
- **multipart 字段**：`file`（单文件）。也支持直接上传 **ZIP 包**，服务端安全解压；
- **注意（工程侧联调）**：`/uploadFile` 是同步「落盘 + 解包」，批次包越大响应越慢；`POOL_AUTOSTART=0` 时首次调用还要拉起子进程（`POOL_STARTUP_TIMEOUT` 默认 60 秒），
  平台侧 HTTP 超时建议 **≥90 秒**，反向代理的 body 限额需按真实批次包大小放开（默认 64 MiB 会直接 413）；
- **M01 例外**：`CMA_receive_multimodal_batch` 额外支持 multipart 字段 `files`（多文件）；
- **入口识别**：ZIP/多文件解压后，包内根级恰好一个 `.jsonl` 即为入口；
  若带 `manifest.json`（`crossmodal-manifest-v1`）则以清单 `entrypoint` 为准；
  根级有多个 JSONL 且无清单 → 报错（不猜入口）。

响应（统一信封）：

```json
{"code":0,"msg":"上传成功","data":{
  "uniqueId":"task01_file01","entrypoint":"01_batch_manifest.jsonl",
  "files":["01_batch_manifest.jsonl","media/x.png"],"fileCount":2}}
```

> 各算子 `data` 字段略有差异（有的返回 `inputDir`/`fileCount`），
> **只要 `code=0` 即上传成功**；后续 `/predict` 会自动读取任务 `input/` 目录。
> 重复上传同一 `uniqueId` 会**替换**该任务的输入素材。

### 4.4 `POST /predict`（核心接口）

#### 4.4.1 请求体

| 字段 | 必填 | 说明 |
|---|---|---|
| `uniqueId` | **是** | 任务标识；同一大阶段内所有算子共用同一个值 |
| `isLastOperator` | **是** | **必须是 JSON 布尔**（`true`/`false`，字符串 `"true"` 会被拒绝） |
| `inputFile` | 否 | 阶段首算子**省略**；同一阶段内后续算子传**上一响应** `data.outputFile` 的原值 |
| `config` | 否 | 业务参数覆盖对象；**未在白名单内的键直接报错**（见 6.3） |

> - 请求体**不接受** `params`、`lineageFile`、`stopChain` 等文本算子池的字段；未知字段多数算子会直接返回参数错误。
> - `inputFile` 必须是**当前 `uniqueId` 任务目录内**的路径（阶段首算子除外），直接回传上一响应给的值即可，不要改写。

示例（M01，阶段首算子，阶段末形态）：

```json
{"uniqueId": "task01_file01", "isLastOperator": true}
```

示例（同阶段第二个算子，带业务参数）：

```json
{"uniqueId": "task01_file01",
 "isLastOperator": false,
 "inputFile": "/data/output/task01_file01/multimodal_batch_intake/run001/01_workitems.jsonl",
 "config": {"enabled": true}}
```

#### 4.4.2 字段别名（个别算子）

| 算子 | 差异 |
|---|---|
| M18 / M19 / M22 | 业务参数字段名为 **`overrides`**（不是 `config`），语义完全一致 |
| M23 / M26 | **同时**接受 `config` 与 `overrides`，二者等价 |
| M26 | `uniqueId` 也接受 snake_case 写法 `unique_id`（二者同时给出且不一致会报错） |
| M14 | 请求体忽略未知字段（其它算子多为直接拒绝） |

> 建议统一按 `config` 传参；若目标算子返回「未知字段」，改用 `overrides` 重试。

#### 4.4.3 响应体（v4.2 统一契约）

统一信封 `{"code": 0|1, "msg": "...", "data": {...}}`。业务成功必须同时满足 HTTP 200 与 `code=0`。

**形态二（JSON）**：`data` 统一为 `{operator, status, outputFile, result}`，**中间调用与阶段末一致**（不再返回 `lineageFile`）：

```json
{"code":0,"msg":"success","data":{
  "operator":"multimodal_batch_intake",
  "status":"success",
  "outputFile":{
    "format":"crossmodal-files-v1",
    "entrypoint":"01_workitems.jsonl",
    "fileCount":6,"totalBytes":31240,
    "files":[{"path":"01_workitems.jsonl","encoding":"utf-8","size":9822,"content":"..."}]},
  "result":{
    "status":1,"process_status":"success",
    "statistics":{"registered":7,"conservation_ok":true}}}}
```

- `data.outputFile`：`crossmodal-files-v1` 内容对象（平台物化后作为下一算子 `inputFile`）；
- `data.result`：业务摘要，记录级 `status` 为 int（判定型 1 通过/0 不通过；处理型 1 成功/0 失败），并附 `process_status` 细分状态；
- 业务失败（`code=1`）时 `data` 为空对象 `{}`，`msg` 说明原因（参数校验失败仍返回 HTTP 422）。

**形态一（multipart 单文件流）**：响应为 JSON，首字段 int `status`（1 成功/0 失败；判定型 1 通过/0 不通过），其余为业务字段；M05/M06/M07 成功时返回文件流（`FileResponse`）。

#### 4.4.4 形态一压缩包模式（v4.3，#3–#21 共 19 个算子）

**请求**：

```text
POST /predict?detection=<算子别名>[&uniqueId=<任务id_文件id>]
Content-Type: multipart/form-data; boundary=...
file=<ZIP 包二进制>
（可选）普通表单字段：业务参数，如 enabled=true / threshold=0.5 / max_frames=8
```

- `detection` 取值与 `operatorId` 同一张注册表（Mxx/xx/x/英文 id/目录名，大小写不敏感），也接受请求头 `X-Detection`；
- ZIP 包内约定：**入口 JSONL 在包内任意相对路径**（推荐根目录），媒体按记录中的相对路径放在包内；可带 `manifest.json`（`{"format":"crossmodal-manifest-v1","entrypoint":"<相对路径>"}`）。无清单时按「唯一的顶层 JSONL」识别，入口不唯一会报错；
- `uniqueId` **可省略**；省略时服务端生成 `upload_<YYYYmmdd_HHMMSS_ffffff>`（该值可通过响应里的 `uniqueId` 取回）。显式传入时必须符合「任务id_文件id」格式，纯数字/单词会被 HTTP 422 拒收；
- 请求体上限 256 MB（`MAX_UPLOAD_BYTES`）；解压成员数与解压总大小也有上限（`FORM1_MAX_ZIP_FILES`=50000、`FORM1_MAX_UNPACKED_BYTES`=8 GiB，可用环境变量调整），并拒绝绝对路径、`..` 穿越和符号链接。

> **业务参数放 body 的正确方式**：形态一（单文件流）的业务参数必须作为 **multipart/form-data 的普通表单字段**
> 与 `file` 一起提交，例如 `-F "file=@input.zip" -F "enabled=true" -F "duration_max_diff_sec=2"`。
> **不要把 JSON 对象直接当 body**：`Content-Type: application/json` 会进入形态二，需要
> `uniqueId`/`isLastOperator`/`inputFile`/`config` 字段，缺字段或顶层出现业务参数会返回 HTTP 400
> `{"code":1,"msg":"未知字段：..."}` 或 `{"code":1,"msg":"isLastOperator 必须是布尔值"}`。
> 形态一的业务失败是 HTTP 200 + `{"status":0,...}`，**不会**返回 400；看到 400（`code` 信封）说明走的是形态二。
> 另：`detection` 仍应放在 URL 查询参数上，供池化入口路由。

**成功响应**（HTTP 200，`status=1`）：顶层字段全部平铺，无 `code/msg` 信封。

```json
{"status":1,"process_status":"success","uniqueId":"t8_09","operator":"candidate_description",
 "outputFile":{"format":"crossmodal-files-v1","mode":"path-reference",
   "runDir":"/data/output/t8_09/candidate_description/run001",
   "entrypoint":"09_descriptions.jsonl","manifest":"manifest.json",
   "files":["09_descriptions.jsonl","09_rejects.jsonl","09_rewrite_tasks.jsonl","manifest.json","media/x.jpg"],
   "fileCount":5,"totalBytes":31240,
   "zip":"/data/output/t8_09/candidate_description/run001_form1.zip","zipBytes":2311},
 "result":{"status":"success","statistics":{"records":52,"described":52}},
 "sample_id":"f8k-0001","description":"A black woman ..."}
```

| 字段 | 含义 |
|---|---|
| `status` | **执行状态**：1=本批成功执行/0=执行失败（参数、解包、运行异常）。**业务判定**看 `process_status`/`result` 及各算子原有业务字段 |
| `process_status` | 业务过程态：`success` / `failed` / `not_applicable` / `pending_review` / `route_disabled` / `pending_writeback` 等 |
| `uniqueId` | 本次任务标识（显式传入则原值返回，否则服务端生成） |
| `operator` | 算子英文短名（如 `data_prescreen`、`normalize_image`） |
| `outputFile` | 路径引用对象，见 §7.1；`outputFile.zip` 可直接作为下一算子形态一的 `file` |
| `result` | 该算子原有业务摘要（统计、样本级结果等） |
| 其余字段 | 原形态一单文件响应的业务字段（如 `text`/`band`/`admission`/`pairs`），原样平铺到顶层 |

**失败响应**（HTTP 200，`status=0`；参数校验类仍为 HTTP 422）：

```json
{"status":0,"msg":"压缩包内入口不唯一（a.jsonl, b.jsonl），请在包内提供 manifest.json 的 entrypoint 字段"}
```

**注意事项**：

1. 非 ZIP 单文件调用仍走 v4.2 原逻辑：M04 单记录、M08/M09/M10/M11 单 JSON/JSONL、M12–M19 单 JSON/JSONL 不变；M05/M06/M07 非 ZIP 仍返回文件流（`FileResponse`）；
2. ZIP 模式不会把运行目录下的 `input/`、`__pycache__/`、`*.log`、`config.snapshot.json`、旧 `*_form1.zip` 打进输出包；
3. 输出包的 `manifest.json` 由服务端统一重写为 `crossmodal-manifest-v1`（`format`/`entrypoint`/`artifacts`/`files[]`），不会与运行目录自带 manifest 重名；
4. `runDir`/`zip` 是**容器内绝对路径**；平台与算子同机共享 `OUTPUT_DIR` 时可直接读取，否则请以 `outputFile.files[]`/`outputFile.zip` 为准。

#### 4.4.5 常见输入错误：纯图片/无入口 ZIP

**现象**：

```json
{"status":0,"msg":"素材包必须包含 manifest.json 或唯一 JSONL 入口"}
```

**原因**：上传的 ZIP 里没有「入口 JSONL」（也没有 `manifest.json` 声明 `entrypoint`）。
#3–#21 的形态一输入是**阶段包 = 记录清单 JSONL + 相对路径媒体**，不是图片集合；纯图片 ZIP 没有记录清单，
会在入口定位阶段被拒绝。这不是接口/模型故障。

- 测 #3 `filter_irrelevant_data`：用 `deliver_dataset_1023` 这类「`manifest.json` + `02_scene_verified.jsonl` + `media/`」的包；
- 测 #12 `score_image_text_consistency`（图文匹配打分）：必须用 #11 产出的**候选对 JSONL** 包
  （`pair_id`/`left`/`right`/`evidence` 等），**不能**直接用纯图片，也不能直接用记录级 `02_scene_verified.jsonl`；
- 测 #12 的最快方式：把 #11 响应的 `outputFile.zip` 直接作为 #12 的 `file` 上传（§5.2）。

**正确包结构**：

```text
stage_input.zip
├── manifest.json          # {"format":"crossmodal-manifest-v1","entrypoint":"records.jsonl"}（可省略，但需保证顶层唯一 JSONL）
├── records.jsonl          # 每个算子要求的记录结构（如 #12 的候选对）
└── media/...              # 记录中的相对路径媒体
```

> 排查提示：若调用的确实是 #12，却返回上面 #3 的文案，说明服务端进程仍在运行旧代码（文件已替换但未重启），
> 重启池化入口后重试。可直接用 `crossmodal_test8_upload\_business_pkgs\` 下的两个包做最小回归。

#### 4.4.6 常见输入错误：上传 ZIP 不完整/被截断

**现象**：

```json
{"status":0,"msg":"该算子需要 JSON/JSONL 输入"}
```

**原因**：请求里 `file` 字段的字节内容**不是有效 ZIP**（网关/客户端把 250 MB+ 的大包截断、改写，
或传成了 base64/文本/文件路径字符串）。算子内部先判断 `zipfile.is_zipfile()`，失败后按「单文件」
处理；上传文件名又不是 `.json`/`.jsonl`，于是返回该提示。它不是数据或模型问题。

**快速判断**：

1. 先用官方小包 `dataset_delivery_test\deliver_dataset_1023_smoke40_image.zip`（2.78 MB）走同一入口；
   返回 `status=1` 说明算子代码正常，问题在**大文件上传链路**；
2. 在服务器容器内 `curl` 本机池化入口（绕开平台网关）上传同一个 ZIP；成功则确认是平台网关/客户端问题；
3. 检查失败请求对应任务目录 `OUTPUT_DIR/<uniqueId>/input/` 下收到的文件：
   大小应等于 266,214,429 字节（`deliver_dataset_1023.zip`），且 `zipfile.is_zipfile()` 为 True；
   若实际文件偏小/为空/不是 ZIP，即为上传截断。

**处理建议**：

- 平台/网关 body 上限调到 **≥300 MB**（Nginx `client_max_body_size 300m;`）、上传超时 ≥300 秒；
- 必须用 **二进制文件流** 上传，不要 base64/文本读取/二次压缩，不要只传本地路径字符串；
- 大包联调先用小包（`deliver_dataset_1023_smoke40_image.zip` 或 `crossmodal_test8_upload\_business_pkgs\m03_dataset_mini.zip`），
  全量 872 条数据建议按 ≤100–200 条拆批上传；
- 同一份 ZIP 两端比对 SHA256：`deliver_dataset_1023.zip` 应为
  `391ebeb05bfa2821360b0abf380872e71ddaf28f19861d8f50a95ba9dc81a39d`。

#### 4.4.7 路径输入 `filePath`（v1.1 新增）

形态一除 multipart `file` 上传外，还支持直接传**池进程可读的本地文件绝对路径**，由池化入口
`inference.py` 读成文件流后转发给子算子。适合平台按路径驱动链路：平台只需把上一步响应的
`outputFile.zip` 路径原样传给下一步，**不需要下载、解压或还原 `files[]`**。

```bash
# 方式 A：query 参数（其余表单字段可继续用 urlencoded 传）
curl -X POST "http://<host>:17059/predict?detection=clean_normalize_text&uniqueId=task01_file01&filePath=/data/output/upload_xxx/data_prescreen/run001_form1.zip"

# 方式 B：JSON body（标量字段会转成表单字段转发）
curl -X POST "http://<host>:17059/predict?detection=clean_normalize_text" \
     -H "Content-Type: application/json" \
     -d '{"filePath": "/data/output/upload_xxx/data_prescreen/run001_form1.zip",
          "uniqueId": "task01_file01"}'
```

`filePath` 可放在 **query**、**urlencoded 表单** 或 **JSON body**（字段名兼容 `file_path`/`filepath`）。
规则：

1. **只对 `/predict` 生效**；`/uploadFile`、`/removeFile` 和形态二 JSON 的 `inputFile` 路径不变；
2. `filePath` 与 multipart `file` **二选一**，同时传返回 400；
3. `filePath` 必须是**绝对路径**、存在且为普通文件；路径按**池容器内路径**理解
   （如响应里的 `/data/output/...`），部署方也可以传宿主机挂载后的容器路径；
4. 按当前部署要求**不做目录白名单**，只校验绝对路径/普通文件/大小上限 `MAX_UPLOAD_BYTES`；
   该接口属于内部服务，请通过网关/网络隔离限制调用方；
5. `uniqueId` 仍可省略；`config`/`isLastOperator` 等标量字段可放在 query、urlencoded body
   或 JSON body 顶层，会一并转成表单字段；
6. 路径不存在/相对路径/目录 → 返回 400 `{"code":1,"msg":"filePath 参数错误：..."}`；
   文件超过上限 → 413；响应头带 `X-Pool-Input: filePath` 表示本次走了路径模式；
7. 文件大小上限沿用 `MAX_UPLOAD_BYTES`（compose 默认 2 GiB）；池化入口按流式转发，不整体读入内存。

链路示例（首步仍用 `file`，后续全部 `filePath`）：

```text
#3  file = 原始数据集.zip                → outputFile.zip
#4  filePath = #3 的 outputFile.zip      → outputFile.zip
#5  filePath = #4 的 outputFile.zip      → ...
```

详细变更、测试与部署见 `_v1.1路径输入说明.md`。

### 4.5 `POST /removeFile?uniqueId={任务id}`

删除该任务工作区（输入素材、阶段产物、血缘）。幂等：

```json
{"code":0,"msg":"删除完成","data":{"uniqueId":"task01_file01","removed":true}}
```

需要**强制重跑**某个任务时，先 `removeFile` 清理，再重新上传调用。

### 4.6 状态码与错误处理（重要）

**判断调用是否成功，请以响应体 `code` 字段为准**，不要只看 HTTP 状态码：

| HTTP | `code` | 场景 |
|---|---|---|
| 200 | 0 | 成功 |
| 200 | 1 | 业务失败（配置非法、输入不存在、运行失败、任务被锁等），`msg` 含原因 |
| 422 | 1 | 请求参数不合法（缺 `uniqueId`、`isLastOperator` 非布尔、`config` 含未知键等） |
| 413 | 1 | 上传超过该算子限额 |
| 404 | 1 | 接口不存在（本包**不提供** `/downloadFile`） |
| 400 | 1 | 池化层：缺少或无法识别 `operatorId` |
| 502 | 1 | 池化层：转发到算子进程失败 |
| 503 | 1 | 池化层：算子进程启动失败/未就绪（看 `data.msg` 与 `/operators` 的 `lastError`） |

## 5. 调用流程（编排口径）

```text
        ┌─ 大阶段 N（同一 uniqueId） ────────────────────────────────┐
上传 → │ 算子1 (省略 inputFile)                                     │
        │   └→ data.outputFile（crossmodal-files-v1）──┐             │
        │ 算子2 (inputFile = 上一步 outputFile 原值) ←─┘             │
        │   └→ data.outputFile（crossmodal-files-v1）──┐             │
        │ …                                  │                      │
        │ 阶段末算子 (isLastOperator=true, inputFile = 上一步的值)   │
        └─→ data.outputFile（crossmodal-files-v1 内容对象）┘         │
                              ↓ 工程侧落库/落 OSS
        ┌─ 大阶段 N+1（新 uniqueId）────────────────────────────────┐
        │ 把上一阶段产物作为文件重新 uploadFile → 从该阶段首算子开始  │
        └───────────────────────────────────────────────────────────┘
```

具体步骤：

1. **分配 `uniqueId`**：一个任务（一个数据单元）一个标识，例如 `task20261012_file001`；
2. `POST /uploadFile?uniqueId=<uid>&operatorId=M01` 上传该任务的输入素材；
3. **同一大阶段内逐算子 `POST /predict`**（同一 `uid`，按 6.1 表的阶段内顺序）：
   - 阶段**首个算子**：省略 `inputFile`（自动取任务 `input/` 目录的入口）；
   - 阶段内**后续算子**：`inputFile` = 上一响应 `data.outputFile` 的**原值**（`crossmodal-files-v1` 内容对象/入口引用；v4.2 起中间调用也返回）；
   - 想中途查看结果：读该响应的 `data.outputFile`/`data.result`（与阶段末同构）；
4. **阶段末算子**：传 `isLastOperator=true` → 得到 `data.outputFile` 内容对象与业务摘要 `data.result`，
   由工程侧保存（落 OSS / 数据库）；
5. **进入下一大阶段**：把上一阶段产物按 `files[].path` **还原为文件**，
   打包为 ZIP（或直接上传入口 JSONL），用**新的 `uniqueId`** 调 `/uploadFile`，
   再从该阶段首算子开始；
   > 同机部署且共享 `OUTPUT_DIR` 时，也可以直接读取磁盘上 `OUTPUT_DIR/<uid>/…` 的真实产物文件。
6. **清理**：任务处理完成后调 `/removeFile?uniqueId=<uid>` 释放空间。

**关于重复调用**：同一 `uniqueId` 的任务目录带任务锁，并发写会被拒绝；
部分算子在输入未变时会**复用**上次运行结果。需要完全重跑请先 `removeFile`。

### 5.1 将阶段末 `outputFile` 还原为下一阶段输入

阶段末响应建议完整保存为 `stage_response.json`，再执行下面的通用脚本。脚本会同时处理 UTF-8 文本和
base64 二进制文件，并拒绝越界路径；还原后的目录可以直接压缩上传。

```python
import base64
import json
from pathlib import Path

response = json.loads(Path("stage_response.json").read_text(encoding="utf-8"))
if response.get("code") != 0:
    raise RuntimeError(response.get("msg", "阶段执行失败"))

bundle = response["data"]["outputFile"]
if bundle.get("format") != "crossmodal-files-v1":
    raise ValueError("响应不是 crossmodal-files-v1")

root = Path("next_stage_input").resolve()
for item in bundle.get("files", []):
    rel = Path(item["path"])
    if rel.is_absolute() or ".." in rel.parts or "\\" in item["path"]:
        raise ValueError(f"非法产物路径: {item['path']}")
    target = (root / rel).resolve()
    target.parent.mkdir(parents=True, exist_ok=True)
    if root not in target.parents and target != root:
        raise ValueError(f"产物路径越界: {item['path']}")
    if item.get("encoding") == "base64":
        target.write_bytes(base64.b64decode(item["content"]))
    else:
        target.write_text(item["content"], encoding="utf-8")

print("下一阶段入口:", root / bundle["entrypoint"])
```

还原后可直接上传入口 JSONL：

```powershell
curl.exe -X POST "http://127.0.0.1:8100/uploadFile?uniqueId=task01_stage02&operatorId=M04" `
  -F "file=@next_stage_input/01_workitems.jsonl"
```

若阶段产物包含多个文件，建议把 `next_stage_input` 整体压缩成 ZIP 上传；服务会根据
`manifest.json` 的 `entrypoint` 识别入口，未提供清单且根目录存在多个 JSONL 时不会猜测入口。

### 5.2 逐算子直传（v4.3 形态一压缩包链路，推荐）

业务平台不落地上传中间的 `outputFile.files[]` 时，可直接把每个算子返回的
`outputFile.zip` 作为**下一个算子**的 `file` 上传，形成「一算子一请求」的流水线：

```powershell
# 1) 用上游阶段产物（入口 JSONL + 媒体 + manifest.json）打第一个包
curl.exe -X POST "http://127.0.0.1:8100/predict?detection=filter_irrelevant_data&uniqueId=task01_file01" `
  -F "file=@stage_input_03.zip"

# 2) 取响应 outputFile.zip，直接喂给下一个算子（detection 别名见 6.1）
#    假设响应保存为 m03.json，用 Python 取 outputFile.zip 路径
$zip = (Get-Content m03.json -Raw | ConvertFrom-Json).outputFile.zip
curl.exe -X POST "http://127.0.0.1:8100/predict?detection=clean_normalize_text&uniqueId=task01_file02" `
  -F "file=@$zip"

# 3) 重复至 #21（detection 别名 = 6.1 表「英文别名」列，去掉 CMA_ 前缀）
curl.exe -X POST "http://127.0.0.1:8100/predict?detection=dispose_mismatched_sample" `
  -F "file=@<上一步 outputFile.zip>"
```

要点：

- 每个算子响应顶部 `uniqueId` 是本次任务标识；不传 `uniqueId` 时由服务端生成，**不会**影响链路；
- `status=1` 表示该算子成功执行（文件已产出、`outputFile.zip` 已生成）；业务结论（通过/隔离/待人工等）看 `process_status` 与 `result`；
- `outputFile.zip` 由算子自动生成，包含入口 JSONL、媒体和重写后的 `manifest.json`，**可直接作为下一算子输入**，无需再处理 `files[]`；
- 平台若需要按路径取产物，使用 `outputFile.runDir` + `outputFile.entrypoint`（容器内绝对路径，见 §7.1）。

## 7. 阶段间传输格式 `crossmodal-files-v1`

阶段末 `data.outputFile` 是一个「文件内容对象」，把该阶段运行目录下的产物**内联**返回：

| 字段 | 含义 |
|---|---|
| `format` | 固定 `crossmodal-files-v1` |
| `entrypoint` | 主入口文件名（如 `01_workitems.jsonl`）——下一阶段的第一步读取它 |
| `fileCount` / `totalBytes` | 打包文件数 / 总字节数（部分算子可能不返回这两个字段） |
| `files[]` | 每个成员：`{path, encoding, size, content}` |

编码约定：

- **文本文件**（`.jsonl`/`.json`/`.txt`/`.md`/`.log`/`.csv`/`.yaml`…）→ `encoding: "utf-8"`，`content` 为字符串；
- **二进制文件**（图片、音视频等）→ `encoding: "base64"`，`content` 为 base64 字符串；
- `path` **只允许包内相对路径**；绝对路径、`..`、反斜杠一律被拒绝。

使用注意：

1. 内容对象**不含**上一阶段之外的文件，也不含任务 `input/` 里的原始素材（按需由工程侧自行保存）；
2. 超过该算子 `MAX_RESPONSE_BYTES` 时**直接失败，不做截断**——这是刻意的，避免拿到半份数据却以为成功；
3. **【v4.2 停用】** 血缘文件 `lineage.json` / 阶段上下文 `stage_context.json` / 拼接血缘 `stage_lineage.jsonl` /
   阶段归档 `stage_artifact.zip` **不再产出、不再作为成员**；运行清单 `manifest.json` 与运行日志仍随内容对象返回，便于溯源；
4. 下一阶段入口：按 `files[].path` 还原文件后取 `entrypoint` 那个 JSONL 作为输入
   （或整体打包 ZIP 上传，服务端会自动识别入口）。

### 7.1 路径引用变体 `mode=path-reference`（v4.3 形态一）

形态一压缩包模式的 `outputFile` 不再内联文件内容，而是给出**运行目录的路径引用**：

| 字段 | 含义 |
|---|---|
| `format` | 固定 `crossmodal-files-v1` |
| `mode` | 固定 `path-reference`（与形态二内联内容对象区分） |
| `runDir` | 本次运行的输出目录**容器内绝对路径**（如 `/data/output/<uid>/<operator>/run001`） |
| `entrypoint` | 主入口文件名（相对 `runDir`，如 `16_whole_alignment.jsonl`） |
| `manifest` | 固定 `manifest.json`（位于 `runDir` 内，`format=crossmodal-manifest-v1`，记录入口/artifacts/files 清单） |
| `files[]` | 成员相对路径列表（不含 `input/`、日志、缓存、旧 `*_form1.zip`） |
| `fileCount` / `totalBytes` | 成员数 / 总字节数 |
| `zip` | 输出压缩包**容器内绝对路径**（`<runDir>_form1.zip`） |
| `zipBytes` | 压缩包大小 |

使用约定：

1. **平台按路径取产物**：与算子同机且共享 `OUTPUT_DIR` 时，直接读 `runDir`/`entrypoint`；否则下载/挂载该目录；
2. **直传下一算子**：把 `zip` 路径对应的文件作为下一算子形态一的 `file` 上传即可（包内已含入口、媒体和重写的 `manifest.json`），无需还原 `files[]`；
3. `runDir`/`zip` 是容器内路径，跨容器调用时应通过平台侧的文件服务/共享卷对齐；
4. 内容对象（形态二）与路径引用（形态一包模式）**不会同时出现**：同一算子的两种调用协议各自返回各自契约，互不影响。

**工程侧怎么取到具体文件（重要）**

当前包**不提供 HTTP 下载接口**（`/downloadFile` 返回 404，这是设计约定）；`outputFile` 本身就是
「容器内路径」，工程侧通过**共享输出卷**读取，不需要再调接口。

- `docker-compose.yml` 默认把宿主机目录
  `${OUTPUT_HOST_DIR:-/data/webapp/idg/数据工程产线算子/operator-output/opcrossmodalpool}`
  挂到容器 `/data/output`；因此容器路径 `/data/output/...` 在宿主机上就是
  `${OUTPUT_HOST_DIR}/...`，两者相对路径完全一致。
- 以一次真实响应为例：

  | 响应字段 | 容器内路径 | 宿主机路径 |
  |---|---|---|
  | `outputFile.runDir` | `/data/output/upload_xxx/data_prescreen/run001` | `$OUTPUT_HOST_DIR/upload_xxx/data_prescreen/run001` |
  | `outputFile.entrypoint` + `runDir` | `.../run001/02_screened.jsonl` | `$OUTPUT_HOST_DIR/upload_xxx/data_prescreen/run001/02_screened.jsonl` |
  | `result.outputFile` | `/data/output/upload_xxx/02_screened.jsonl` | `$OUTPUT_HOST_DIR/upload_xxx/02_screened.jsonl` |
  | `outputFile.zip` | `/data/output/upload_xxx/data_prescreen/run001_form1.zip` | `$OUTPUT_HOST_DIR/upload_xxx/data_prescreen/run001_form1.zip` |

- 在部署机确认实际挂载目录：

  ```bash
  docker inspect opcrossmodalpool --format '{{range .Mounts}}{{println .Source "->" .Destination}}{{end}}'
  grep -n 'OUTPUT_HOST_DIR' docker-compose.yml .env 2>/dev/null
  ```

  拿到宿主机目录后直接读/拷贝：

  ```bash
  OUTPUT_HOST_DIR=/data/webapp/idg/数据工程产线算子/operator-output/opcrossmodalpool
  UID_DIR="$OUTPUT_HOST_DIR/upload_20261029_154413_697624"
  ls -lh "$UID_DIR/data_prescreen/run001/"
  head -n 2 "$UID_DIR/data_prescreen/run001/02_screened.jsonl"
  unzip -l "$UID_DIR/data_prescreen/run001_form1.zip"
  ```

- 若工程侧是**另一台机器/另一个平台服务**：把同一个宿主机目录挂载到工程侧服务（NFS/共享盘或
  compose volume），按上面相对路径读取；或先同步到对象存储。**不要**通过算子池 HTTP 端口取文件
  （池只暴露 `/predict`、`/uploadFile`、`/removeFile` 等业务接口，子算子 8101–8126 仅容器内可见）。
- `outputFile.zip` 已包含 `entrypoint` + `files[]` + 重写后的 `manifest.json`，工程侧只取这一个 ZIP
  也能拿到完整产物；需要单文件时按 `runDir + files[]` 读取。
- 临时救急可用 `docker cp opcrossmodalpool:/data/output/<uid>/.../run001_form1.zip ./`，但生产建议共享卷。
- 如确实需要 HTTP 下载接口（平台不能挂共享卷），可另行在池化入口增加受限的 `GET /downloadFile`
  （只允许 `OUTPUT_DIR` 下路径），属于额外开发项，需要更新 `inference.py` 并重启。

> **v1.1 起**：跑链路时平台甚至不需要读取/挂载产物——直接把 `outputFile.zip` 的容器内路径
> 作为下一算子的 `filePath` 传入即可（§4.4.7），由池化入口读文件并转发；只有**最终交付**
> 需要把最终 `outputFile.zip` 保存/落库时才需要工程侧取文件。

26 个算子统一内置 `utils/mty_compliance.py`（同一份实现，按算子注入阶段号与阶段末标记），
补齐甲方《MTY 规范》与流程图要求，**不改动任何业务算法与接口契约**：

| 规范条目 | 实现 | 产物/字段 |

| 第 7 条 / 流程图「阶段产物」 | 阶段末算子额外产出：`stage_lineage.jsonl`（该阶段全部血缘**拼接文本，一条记录一行**）与 `stage_artifact.zip`（拼接血缘 + 该阶段文本类产物 + `stage_artifact_manifest.json`） | 落运行目录并登记进 `manifest.json` 的 `artifacts`，随阶段末 `crossmodal-files-v1` 一并交付 |

| 流程图 F2/F3/F4：血缘文本/输出文件/阶段产物上传 OSS | `archive_object` 按 `<前缀>/<阶段>/<任务id>/<文件id>/<运行号>/<文件名>` 上传；未配置对象存储时镜像到本地 `_mty_transport/oss_mirror/<同键>` | `transport_report.json`（含每条归档的 `status/backend/uri/bytes`） |

关键设计（对调用方透明）：

1. **全程不抛异常**：归档或入库失败只写 `status=failed/degraded` 与 `error`，**响应体、状态码、产物内容一律不受影响**；
2. **零依赖降级**：未配置 `MTY_OSS_*` 时用本地镜像目录 + 标准库 SQLite，对象键与库表字段与上云形态完全一致，
   工程侧可据此把镜像与库同步上云；
3. **不暴露部署路径**：本地镜像只回逻辑地址 `local-mirror://<对象键>`，报告里不含宿主机绝对路径；
4. **隔离在 `OUTPUT_DIR` 之外**：镜像与库默认写在 `<算子目录>/_mty_transport/`，
   `/removeFile` 清理任务目录**不会**删掉归档与关系库；`OUTPUT_DIR` 内仍然只有 `uniqueId` 目录；
5. **对象超大不截断**：单对象超过 `MTY_OSS_MAX_OBJECT_BYTES`（默认 256 MiB）时记 `skipped` 并给出原因，
   媒体文件默认不随血缘上传（`MTY_OSS_INCLUDE_MEDIA=1` 可打开）。

### 7.3 任务级最终输出（阶段末算子增量合并，`task_output.py`）（【v4.2 停用·历史存档】）

> **【v4.2 停用】** 根目录 `task_output.py` 的最终血缘发布逻辑已停用（函数保留存档、标记 `# [v4.2]`），不再产出 `output/lineage/`。以下内容仅作历史契约备查。

《输出格式.md》§3 要求**每个输入源文件一份最终血缘**（`file → stage_segment/oss_supplement × N → outcome → deliver_supplement`）。
实现方式：**每个大阶段（S1–S8）只有阶段末算子在 `/predict` 收尾时增量写入一次**，中间算子不再重复写：

```text
<输出根>/<任务id>/output/
├── lineage/jsonl/lineage_<任务id>_<文件id>.jsonl   # 该文件截至当前阶段的完整血缘（逐阶段增量合并）
└── data/zip/23_deliverable_package.zip             # M23 交付阶段额外归档交付包
```

- **触发点**：阶段末算子（#3/#8/#19/#21/#22/#23/#25/#26）在 `prepare_stage_result` 末尾调用
  包根 `task_output.py` 的 `publish_stage()`；失败只记 warning，绝不影响 `/predict` 响应。
- **合并规则**：扫描输出根下同任务（`<任务id>_<NN>` 目录）、同阶段的全部算子 run 目录，
  把本阶段所有算子的节点合成**一个** `stage_segment` 后并进该文件的最终血缘；
  阶段顺序单调（S1→S8），重跑同阶段**整体替换**该阶段段（幂等）。
- **结局口径**：`REJECT/FAIL` 粘滞；非阻塞 `PENDING`（配额/未抽样/不适用/跳过等）不覆盖已有 `PASS`；
  交付行只在 `verdict=PASS` 时携带 `deliver_supplement`。
- **taskId 来源**：输入清单 → 结果字典 → 血缘文件头（HTTP 链路适配器不传清单，血缘头兜底）。
- 环境变量见 3.4 节 `TASK_OUTPUT_*`；验证回放：`python task_output.py --replay-report <算子测试报告> --task-id <任务id>`。

## 8. 模型与权重

### 8.1 权重清单（v1.0 正式版：逐算子内置到 `<算子目录>/weight/`）

| 模型 | 算子内路径 | 内置算子 | 说明 |
|---|---|---|---|
| CLIP-ViT/B-32 | `<算子目录>/weight/clip/ViT-B-32.pt` | M12、M14、M16、M18、M20 | 表1 冻结架构；每算子各一份；**不支持**换 `ViT-L-14` |
| whisper-base | `<算子目录>/weight/whisper-base/` | M08（转写，默认关闭） | 本地 `transformers` 加载；M13 v2 不加载 |
| YOLOv8n | `<算子目录>/weight/YOLOv8n/yolov8n.pt` | M17（必需）、M12（可选） | 通用类别预填，不改变 CLIP 分档 |
| wav2vec2-base / bert-base-chinese | 不内置 | —（M13 生产不使用） | M13 为规则 CER，复用上游转写；仅实验诊断可显式注入 |

每份权重的字节数与 SHA-256 记录在 `map.json.models`、包根 `weight/README.md` 及各算子 `weight/README.md`。
单算子目录可独立复制运行，不依赖包根 `weight/` 或 `shared_clip/`；Docker 镜像会包含各算子自带权重。

#### 8.2 共享 CLIP 服务（`shared_clip/runtime.py`，v1.0 起为可选优化）

- **v1.0 正式版默认不启用**：M12/M14/M16/M18/M20 各自从本算子 `weight/clip/` 加载；
- 只有产线编排脚本显式启动常驻子进程并设置 `MULTIMODAL_CLIP_SESSION` 时，才会通过**本机 IPC**复用同一份 CLIP 权重，
  同一任务**不会加载第二份** CLIP 权重（产物中标记 `shared_task_instance=true`）；
- `shared_clip/` 目录不存在或未启动时，各算子静默回退本地权重，**不影响单算子独立运行**；
- 若环境变量已设置但连接失败 → **显式报错**，不会偷偷另加载一份权重。

### 8.3 加载与降级语义

- **惰性加载**：只在真正需要时才读权重（如 M08 转写开关关闭时**零模型加载**）；
- **设备**：`auto`/`cpu`/`cuda`，CUDA 不可用则退回 CPU 并记录原因；
- **失败**：`allow_degraded=false`（默认真实口径）→ 直接报错；
  `allow_degraded=true` → 返回 `degraded` 标记与真实原因；
  **绝不用固定分/随机分/规则分冒充模型分数**，`model_identity()` 如实写入血缘。

### 9.1 完整流程（PowerShell，M01 → 阶段末）

```powershell
$BASE = "http://127.0.0.1:8100"
$UID  = "task20261012_file001"
```

## 10. 常见问题

| 问题 | 说明与处理 |
|---|---|
| `/predict` 返回 400 | 池化层没识别到 `operatorId`。用 `?operatorId=M12`、请求头 `X-Operator-Id`，或在请求体里给 `operatorId` |
| `/predict` 返回 422 | 请求体不合法：`isLastOperator` 必须是真正的 JSON 布尔（不能写 `"true"`）；`config` 里含未白名单的键；`uniqueId` 为空 |
| 首次调用某个算子很慢 | 池化按需拉起子进程 + 首次加载模型（CLIP/Whisper 等），属正常；也可用 `POOL_AUTOSTART=1` 预热 |
| 返回 503「算子不可用」 | 该算子进程启动失败。查 `/operators` 的 `state`/`lastError`，常见原因：算子目录不完整、端口被占、依赖缺失 |
| 只拿到 `outputFile`，没看到血缘字段 | v4.2 起血缘输出已停用（不再返回 `lineageFile`），业务结果看 `data.result`，阶段产物看 `data.outputFile` |
| `outputFile` 里没有媒体文件 | 属预期：本包按「只登记链接、不复制媒体」口径设计（如 M01），媒体以链接形式记录在记录中 |
| 阶段末报「超过 MAX_RESPONSE_BYTES」 | 该阶段产物过大。**不会截断**。请分片任务、减少打包产物，或按该算子 `README.md` 调整限额 |
| 模型算子报权重缺失 | v1.0 默认加载 `<算子目录>/weight/`：先确认该算子目录下权重文件齐全（`python inference.py --preflight` 的 `weightBundles.missing`）；仅当显式设置 `MODEL_ROOT` 时才检查外挂目录 |
| 重复上传/重复调用会怎样 | 重复上传同一 `uniqueId` 会替换输入素材；重复 `predict` 部分算子复用上次结果。要完全重跑先 `/removeFile` |
| 报「未知字段」 | 多数字段严格校验。检查是否误传了 `params`/`lineageFile` 等文本算子池字段；M18/M19/M22 的业务参数名是 `overrides` |
| 上传 413 | 超过该算子限额（64–256 MiB 不等，详见该算子 `README.md`），减小包体或按需调整 |
| `/uploadFile` 失败且**同一秒**返回 | 不是算子算死，而是请求被立即拒绝。按序排查：① `uniqueId` 是否为「任务id_文件id」格式；② 路由标识是否被池化层识别（旧包只认 `operatorId`，不认 `?detection=`，会 400「缺少或无法识别的 operatorId」）；③ 网关/反代 body 限额（413）；④ `/operators` 里该算子 `state`/`lastError` |
| 上传很慢或超时 | `POOL_AUTOSTART=0` 冷启动需拉起子进程（默认最多 60 秒）+ 大包同步解包；平台侧超时请设 **≥90 秒**，或先用 `GET /ready` 预热（`readyCount=26`），并尽量把批次包拆小 |
| zip 包在 Linux 上解压出现乱码目录 | 用 `python3 -m zipfile -e xxx.zip .` 或 `bsdtar -xf` 解压（勿用老版 `unzip`） |
| 想确认某个算子的输入输出字段 | 看该算子目录下的 `dataset/DATA_SCHEMA.md`（数据契约）与 `README.md`（接口与示例） |
