# 跨模态前后端联调部署说明

本目录 `crossmodal_v1.0` 基于 `crossmodal_v1.0_deploy` 整理，适用于先打通前后端调用链路。
保留 26 个算子、2026-11-11 链路修复、原业务配置和本地权重。各业务接口可直接请求。

## 1. 地址与入口

| 项目 | 配置 |
|---|---|
| 镜像 / 容器 / Compose 服务 | `opcrossmodalpool:1.0.0` / `opcrossmodalpool` |
| Compose 宿主机 → 容器 | `17059 → 8100`，可通过 `HOST_PORT` 修改宿主机端口 |
| 主入口 | `inference.py`，按 `operatorId` 或 `detection` 转发到算子子进程 |
| 业务接口 | `POST /uploadFile`、`POST /predict`、`POST /removeFile` |
| 状态接口 | `GET /health`、`GET /ready`、`GET /operators` |
| 交互文档 | `/docs`、`/redoc`、`/openapi.json` |
| 内部算子端口 | 8101–8126，仅容器内部使用 |
| 服务版本字段 | `v1.1.0`，包含 filePath 能力；镜像 tag 沿用 `1.0.0` |

## 2. Docker Compose 启动

在本目录执行：

```bash
docker compose up -d --build
docker compose ps
curl -fsS http://127.0.0.1:17059/health
curl -fsS http://127.0.0.1:17059/operators
```

可选的一键脚本会准备 `.env`、校验 18 个权重并等待健康检查：

```bash
bash deploy.sh
bash verify_service.sh
```

`.env` 由 Compose 自动读取用于变量展开；直接运行 Python 时需自行设置环境变量。
`.dockerignore` 排除宿主机 `.env`，保留 `.env.example`；各算子的 `weight/` 随镜像构建。
修改源码后必须重新构建并重建容器，单纯重启旧容器不会加载新镜像。

## 3. 本地 Python 启动（PowerShell）

```powershell
cd "G:\HYQX\算子\跨模态\crossmodal_v1.0"
python -m pip install -r requirements.txt
$env:OUTPUT_DIR = "G:\data\crossmodal_integration_output"
$env:POOL_AUTOSTART = "0"
$env:HF_HUB_OFFLINE = "1"
$env:TRANSFORMERS_OFFLINE = "1"
$env:YOLO_OFFLINE = "1"
python inference.py --preflight
python -m uvicorn inference:app --host 0.0.0.0 --port 8100
```

本地直启访问 `http://127.0.0.1:8100`，Compose 则访问宿主机 `17059`。
`POOL_AUTOSTART=0` 时首次调用按需启动子算子；`/ready` 同时报告已启动算子数，
不能仅凭它返回 200 判断所有模型路线均已执行。

## 4. 前后端链路调用

推荐先用 ZIP 直传验证：

```bash
curl -X POST "http://127.0.0.1:17059/predict?detection=clean_normalize_text" \
  -F "file=@stage_input.zip" -F "enabled=true"
```

收到 `outputFile.zip` 后，可将服务端可读的绝对路径传给下一个算子：

```bash
curl -X POST "http://127.0.0.1:17059/predict?detection=generate_candidate_pair" \
  -H "Content-Type: application/json" \
  -d '{"filePath":"/data/output/task/previous_form1.zip","enabled":true}'
```

实际路径使用上一响应中的 `outputFile.zip`；根据真实链路顺序替换算子。
`file` 与 `filePath` 二选一。也可使用上传后执行的 JSON 协议：

```bash
curl -X POST "http://127.0.0.1:17059/uploadFile?operatorId=M04&uniqueId=integration_demo" \
  -F "file=@stage_input.zip"
curl -X POST "http://127.0.0.1:17059/predict?operatorId=M04" \
  -H "Content-Type: application/json" \
  -d '{"uniqueId":"integration_demo","isLastOperator":false,"config":{"enabled":true}}'
curl -X POST "http://127.0.0.1:17059/removeFile?operatorId=M04&uniqueId=integration_demo"
```

接口参数和各算子业务字段见 [使用说明](跨模态算子使用说明.md)、
[单算子调用接入文档](跨模态算子-单算子调用接入文档.md)。业务开关维持来源目录配置，
调用成功不代表全部路线开启或业务审核通过；待模型、待人工等状态仍按原规则返回。

浏览器前端跨域访问时，可由前端开发服务器或网关将 `/api` 代理到池化服务；
后端直连本服务使用上述 HTTP 地址。

## 5. 输出、模型与构建参数

- Compose 输出挂载：`${OUTPUT_HOST_DIR}:/data/output`，默认宿主路径为
  `/data/webapp/idg/数据工程产线算子/operator-output/opcrossmodalpool`，按现场目录修改。
- `filePath` 必须是池进程可读的绝对路径；容器内优先复用上一响应的输出路径。
- Compose 限额固定在 `docker-compose.yml`：上传 2 GiB、解压 4 GiB、文件数 2000、响应 1 GiB。
  `.env` 中的同名值只用于本地直启说明，容器运行以 Compose 显式值为准。
- 模型由各算子内置 `weight/` 加载，离线运行；`MODEL_ROOT` 仅用于显式覆盖权重根目录。
- 默认支持 CPU；`EXPECT_CPU=1` 时验收脚本检查设备为 CPU。GPU 环境验收可设 `EXPECT_CPU=0`。
- 构建源可通过 `.env` 的 `PYTHON_IMAGE`、`PIP_INDEX_URL`、`PIP_TRUSTED_HOST`、`APT_MIRROR` 修改。
  `TORCH_INDEX_URL` / `TORCH_VERSION` / `TORCHVISION_VERSION` 可选择 CPU 轮子。
- Dockerfile 安装 `ffmpeg`、`tzdata`、`libgomp1`；本地直启需另外提供 `ffmpeg` 和 `ffprobe`。
- K8s 使用 [k8s/README-k8s.md](k8s/README-k8s.md)，构建机 CPU 架构需与运行节点匹配。

## 6. 验收与排查

```bash
bash verify_service.sh          # 在已运行的 Compose 容器内验收
bash verify_service.sh --local  # 请求宿主机 HOST_PORT，跳过本地预检
python verify_service.py --port 8100
python inference.py --preflight
```

验收覆盖状态接口、26 个算子、18 个权重 SHA-256、ffmpeg/ffprobe、目录预检、
本地模型环境及可选 CPU 设备检查。接口文档可在浏览器直接打开 `/docs`。

端口不通时查看 `docker compose ps`、`docker compose logs --tail=200`；
模型或媒体处理失败时先检查预检结果、权重完整性和 ffmpeg/ffprobe。
回滚使用保留的旧目录与旧镜像，输出持久化目录继续复用；不要删除业务产物卷。
