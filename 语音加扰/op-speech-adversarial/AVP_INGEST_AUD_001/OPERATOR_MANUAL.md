## 二、功能定义

把用户上传的音频与参考文本**按 `uttid` 精确配对**，产出可供后续加工与评测的语料表；
同时按三项内置规则给出**入库质量提示**（提示不阻断）。

**输入**：ZIP 包，内含音频文件，以及（二选一）同名 `.txt` 或一份清单文件。

**输出**：带 `uttid` 的语料表 `001_corpus.jsonl` + 未入库清单 `001_rejects.jsonl`
+ 入库报告 `001_ingest_report.json`。

**边界**

- ✅ 做：文件扫描、编码/分隔符/表头自适应、`uttid` 归一化与精确匹配、重复检测阻断、
  三项入库质量提示、报告生成。
- ✅ 做（`action=recheck`）：**手动重新检测**——不重扫音频、不改入库结果，只对已入库的
  `001_corpus.jsonl` 复跑三项检测，就地改写报告里的 `checks` 与计数（对应任务书 §1
  「结果只在详情展示，可手动重新检测」）。
- ❌ 不做：音频转码/重采样/裁剪（02 负责）、模糊匹配、数据集权限校验、
  「数据能不能用」的最终裁决（05 质检负责）。

**两种动作（`params.action`）**

| 取值 | 行为 | 产物 |
|---|---|---|
| `ingest`（默认） | 扫音频 + 配文本 + 三项检测 | `001_corpus.jsonl` / `001_rejects.jsonl` / `001_ingest_report.json` |
| `recheck` | 读回已入库语料，只复跑三项检测 | 只更新 `001_ingest_report.json`（`checks.rechecked_at` + `rechecked{}`），语料与拒收清单**逐字节不变** |

`recheck` 的可选参数：`check_min_duration`（临时改判短音频阈值）、`check_allow_gbk` 不适用；
其余入库参数（`dataset_name` / `source` / `manifest_*`）在 `recheck` 下不需要传也不需要重复校验。

## 三、输出内容描述

| 产物 | 内容 | 消费方 |
|---|---|---|
| `001_corpus.jsonl` | 一行一条已入库样本（12 个字段，见 DATA_SCHEMA §2.1） | 02 语音标准化、平台后端入库 |
| `001_rejects.jsonl` | 未入库样本及原因（本算子仅 `missing_text`） | 平台前端「导入结果」页 |
| `001_ingest_report.json` | 清单解析元信息 + 统计 + 三项检测明细 | 平台前端「导入结果」页、血缘 `statistics` |

`data.statistics` 与报告里的 `statistics` **完全一致**（同一份数据，不重复计算）。

前端展示口径：
- `conclusion = success` → 「入库成功」
- `conclusion = partial` → 「部分完成」，并展开未入库清单
- 三项检测有列表非空 → 展示为**黄色提示**，不阻塞下一步

## 四、技术方案

本算子的技术含量不在信号处理，在**格式鲁棒性**与**判定口径可解释**。

### 4.1 清单解析的三段式自适应

1. **编码探测**：UTF-8（含 BOM）→ 失败则探测 GBK/GB18030 → **命中即报错要求转存 UTF-8**。
   *为什么不用自动回退*：静默按 GBK 读会把乱码带进语料表，到评测阶段才暴露，
   排查成本极高。宁可让用户在入库这一步就把文件转好。
2. **分隔符识别**：统计前 50 个非空行的制表符、逗号、空白出现次数，
   优先级 **制表符 > 逗号 > 空格**。空格放最后是关键：参考文本本身含空格，
   过早把空格当分隔符会把一句话切成多列。
3. **表头与列定位**：首行需同时命中「id 类列名」与「文本类列名」才认作表头，
   之后按列名定位；无表头则用「第 1 列 id、第 2 列起拼接」的位置约定。
   一个解析器同时吃 AISHELL（无表头空格分隔）、LibriSpeech（无表头）、
   Common Voice（有表头 TSV/CSV）、JSONL 四种形态。

### 4.2 `uttid` 归一化与精确匹配

`uttid = 文件名去扩展名 + casefold`，全产线统一由 `common/iofs.py::norm_uttid` 提供。
匹配为**精确相等**，不做编辑距离/相似度模糊匹配（原型研发标注硬口径）。

*为什么统一归一化*：真实语料里 `Train_A.WAV` 与 `train_a.wav` 混用是常态，
若各环节各写一套，后续「加扰样本能否回溯到原始样本」必然出错。

### 4.3 重复 `uttid` 阻断

`uttid` 是下游所有表（批次表、质检表、版本 manifest）的主键。存在重复会让样本数
失去意义、按 `uttid` 关联时一对多膨胀，因此在扫描阶段即检查并抛 `duplicate_uttid:`
终止创建，整批不入库。

### 4.4 三项检测的判定方法

| 检测 | 方法 | 阈值来源 |
|---|---|---|
| 短音频 | 从文件头取时长（不解码），`duration < 2.0s` | `checks.min_duration_sec` |
| 空音频 | 解码算 `RMS`，`RMS < 1e-5`（约 -100 dBFS） | `audio.silence_rms` |
| 文本完全重复 | 文本压缩空白后分组，组内 > 1 条即重复 | `checks.normalize_text` |

用 RMS 而非「是否全零」：真实空录音常带极低电平设备底噪，全零判定会漏。

三项检测结果**只进报告，不阻断入库**（任务书 §1 硬口径）。

## 五、技术实现

| 项 | 说明 |
|---|---|
| 语言 | Python 3.9（兼容 3.9+） |
| 音频解码 | `soundfile` 0.13.1（底层 libsndfile，**不依赖 ffmpeg**） |
| 数值 | `numpy` 1.26.4 |
| 配置 | `PyYAML`，`configs/config.yaml` 单一配置源 |
| 服务 | `inference.py`（FastAPI）统一路由，本算子实现 `processor.py::run(ctx)` |
| 中间产物 | 落 `/data/{uniqueId}/tmp/001/`，不复制音频、不做临时转码 |
| 随机性 | **无**（本算子完全确定性，同输入必出同结果） |
| 处理方式 | 单遍扫描，逐条流式处理，内存与样本数无关 |

关键实现点：

- `iofs.parse_manifest()` 返回 `(text_map, meta)`，`meta` 全量写进报告，
  便于用户自查「系统到底怎么理解了我们这份清单」；
- 报告里每个问题列表都有 `io.max_listed` 上限 + `truncated` 计数，
  语料上万条时报告也不会失控，但统计数仍是全量；
- 报告 `manifest` 字段回显 `delimiter` / `header` / `id_column` / `text_column`，
  清单解析出问题时用户能一眼看出系统选了哪个分隔符。

2 条静音、4 条 0.5 秒短音频、3 条重复文本）。

| 指标 | 结果 |
|---|---|
| 匹配准确率 | **100%**（52/52） |
| 缺文本检出率 | **100%**（8/8） |
| 短音频检出率 | **100%**（4/4） |
| 空音频检出率 | **100%**（2/2） |
| 文本重复组检出率 | **100%**（1 组 / 3 条） |
| 重复 `uttid` 阻断 | ✅ 生效 |
| 只提示不阻断一致性 | ✅ 9 条被标记样本全部仍在语料表 |
| 吞吐量 | **206.4 条/秒** |
| 单条平均耗时 | **4.8 ms** |
| 全量检测准确性 | ✅ 全部通过 |

指标由 `utils/measure.py` 在构造的已知真值语料上实测得出，非人工填写。
语料为程序化合成类语音，非真实业务录音。
